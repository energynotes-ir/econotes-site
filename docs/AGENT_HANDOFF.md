# تحویل مدیریت EcoNotes به ایجنت‌ها

## What the user wants

کاربر می‌خواهد مدیریت و توسعهٔ EcoNotes به‌تدریج ایجنت‌محور و تا حد ممکن خودکار شود: واکشی و به‌روزرسانی داده، کنترل کیفیت، محاسبات اقتصادسنجی و شاخص‌های ترکیبی، تحلیل بازار، آماده‌سازی محتوای فارسی، پایش سرویس و انتشار خروجی‌ها. هدف محصول یک میز پژوهش اقتصاد کلان و بازار ایران است که برای تحلیل‌گر و مدیر سرمایه‌گذاری ارزش اشتراکی داشته باشد.

دامنهٔ اصلی فعلی `econotes.ir` است. شروع کار روی متغیرهای مهم بازار ایران بوده و کاربر می‌خواهد در مراحل بعد سناریو، پیش‌بینی، همبستگی پویا، رژیم‌های بازار، رویدادهای مهم و شاخص‌های ساخته‌شدهٔ خودش (از جمله استرس بازار و EPU) هم اضافه شوند. تجربهٔ فعلی سایت عمومی و استاتیک است؛ اتوماسیون کامل تولیدی و دسترسی اشتراکی هنوز برقرار نیست.

## Where things stand

- مخزن: `energynotes-ir/econotes-site`، شاخهٔ `main`، آخرین commit بررسی‌شده: `bdd1284a9c2577bee5290aeee284134e3331dd8c`.
- سایت روی GitHub Pages و دامنهٔ `econotes.ir` منتشر شده است. در بررسی ۳ اکتبر ۲۰۲۶، HTTPS، دامنهٔ اصلی و تغییرمسیر `www` کار می‌کردند؛ اجرای GitHub Actions انتشار موفق بود.
- نسخهٔ منتشرشده استاتیک است. فایل‌های `public/data/` همراه سایت عمومی‌اند و snapshot در `public/data/snapshot.json` زمان و اندازهٔ داده را ثبت می‌کند. snapshot مشاهده‌شده در ۳ اکتبر ۲۰۲۶ شامل ۶۰ سری، ۳۷٬۰۱۶ نقطه و تاریخچهٔ ۶۳۷ اوراق بود.
- فرایند `api/app/refresh_data.py` واکشی زمان‌بندی‌شده دارد، اما فقط وقتی روی دستگاه یا سروری که آن را اجرا می‌کند روشن باشد. زمان‌بند هر پنج دقیقه بررسی می‌کند که منبعی موعد واکشی دارد یا نه؛ این به معنی اجرای دائمی روی GitHub Pages نیست.
- GitHub Actions در `.github/workflows/deploy-pages.yml` با push به `main` یا اجرای دستی، سایت را build و منتشر می‌کند. workflow پایگاه داده را واکشی نمی‌کند و snapshot تازه نمی‌سازد. برای خروجی استاتیک فعلی ابتدا باید داده در SQLite موجود باشد و `npm run prepare:static` اجرا شود.
- SQLite به‌صورت پیش‌فرض در `api/econotes.db` قرار می‌گیرد؛ با `ECONOTES_DB` قابل تغییر است. `compose.yaml` مسیر `/data/econotes.db` را روی volume ماندگار mount می‌کند و سرویس جداگانهٔ `refresh` دارد. Docker و مسیر سروری هنوز جایگزین استقرار استاتیک فعال نشده‌اند و باید در محیط مقصد بررسی شوند.
- پوشش فعلی شامل دو شاخص اصلی بورس TSETMC، USDT/TMN والکس به‌عنوان نمایندهٔ دلار آزاد، نرخ‌های رسمی ETS و بانک مرکزی، فلزات گران‌بها، CPI ایران و آمریکا، نقدینگی و پایه پولی، OMO، بازده اخزا و تاریخچهٔ اوراق است. تعریف دقیق و محدودیت هر گروه در `README.md` آمده است.
- ثبت‌نام، پرداخت و مجوز اشتراک پیاده‌سازی نشده‌اند. همهٔ JSONهای استاتیک عمومی‌اند؛ قرار دادن داده یا تحلیل پولی در این snapshot، آن را برای همه قابل دریافت می‌کند.
- طرح نقش‌های پژوهشی در `docs/AGENT_WORKFLOWS.md` نوشته شده؛ این طرح تعریف نقش‌هاست، نه یک سامانهٔ چندایجنت فعال. دسترسی مرورگر/پایگاه داده برای ایجنت‌ها، صف کار، زمان‌بند وظایف پژوهشی، گزارش‌گیری و هشدار عملیاتی باید جداگانه ساخته شوند.
- در زمان ثبت این handoff، درخت Git پیش از افزودن همین فایل تمیز بود. این فایل هنوز commit یا push نشده است.

## Next step

اولین کار ایجنت بعدی باید تبدیل وضعیت فعلی به یک طرح اجرایی مرحله‌بندی‌شده برای به‌روزرسانی خودکار و ایمن باشد؛ پیش از نوشتن scheduler جدید، اجزای موجود را بازبینی کند تا یک زمان‌بند موازی و ناسازگار ساخته نشود.

1. فهرست منابع و سری‌ها را از `api/app/ingest_*.py`، `api/app/refresh_data.py` و کاتالوگ API استخراج کند. برای هر سری، منبع، تناوب واقعی انتشار، تناوب واکشی، زمان آخرین مشاهده، واحد، حق استفاده، قواعد retry و وضعیت تست را ثبت کند.
2. مسیرهای دوگانهٔ SQLite → API و SQLite → static snapshot را ترسیم کند؛ زمان و گام‌های دقیق تازگی داده را از زمان انتشار سایت جدا کند. مشخص کند کدام داده‌ها مجازند عمومی شوند و کدام داده‌ها در آینده نیازمند API احراز هویت‌شده‌اند.
3. تصمیم فنی کم‌هزینه‌ای برای اجرای دائمی بگیرد. گزینهٔ شروع موجود، Docker Compose با volume ماندگار و worker فعلی است؛ پیش از انتخاب نهایی، پشتیبان‌گیری و بازیابی SQLite، قفل هم‌زمانی، دسترس‌پذیری میزبان و محدودیت‌های استقرار را بررسی کند. اگر اجرای سرور فعلاً ممکن نیست، طرح scheduler بیرونی باید محل پایدار داده و روش امن تولید/انتشار snapshot را مشخص کند؛ runner موقت GitHub Actions نباید تنها محل پایگاه داده باشد.
4. پس از ثبت تصمیم و شکاف‌ها، کوچک‌ترین مرحلهٔ قابل‌سنجش را پیاده کند: گزارش سلامت و تازگی هر منبع، بررسی کیفیت پس از ingestion، و جلوگیری از انتشار snapshot در صورت خطای بحرانی. برای دادهٔ stale یا خراب، هشدار و گزارش قابل‌رسیدگی بسازد؛ مقدار گمشده را جعل یا بی‌صدا درون‌یابی نکند.
5. هر تغییر را با تست‌های موجود و build مربوطه بررسی کند. انتشار عمومی یا تغییر زیرساخت/دامنه را فقط در محدودهٔ مجوزی که کاربر برای همان اقدام داده انجام دهد؛ هیچ secret یا پایگاه SQLite را در مخزن یا پوشهٔ عمومی قرار ندهد.

پس از این ارزیابی، برنامهٔ اجرایی را در یک سند نگه‌داری‌شونده ثبت کند (ترجیحاً به‌روزرسانی `docs/AGENT_WORKFLOWS.md` یا افزودن طرح زیر `docs/aegis/plans/`) و مرحلهٔ اول را کامل کند؛ صرفاً با پیشنهاد معماری متوقف نشود.

## مدل هدف برای اتوماسیون

گردش داده باید قابل ردگیری و idempotent باشد: واکشی منبع → ذخیرهٔ خام/ثبت اجرای واکشی → تبدیل با تعریف نسخه‌دار → کنترل کیفیت → تأیید انتشار سری → ساخت snapshot یا ارائه از API → پایش تازگی و خطا. هر مرحله خروجی ساختاریافته، شناسهٔ ورودی، زمان، نسخهٔ کد/فرمول و خطای قابل‌جست‌وجو ثبت کند.

نقش‌های تعریف‌شده در `docs/AGENT_WORKFLOWS.md` مبنای تقسیم کار باشند:

- **هماهنگ‌کنندهٔ پژوهش:** درخواست را به کارهای مستقل، وابستگی‌ها و مالک هر کار تبدیل کند.
- **پژوهشگر منبع:** تعریف ناشر، API/نمونهٔ پاسخ، تواتر، مجوز و ریسک تغییر منبع را ثبت کند.
- **عامل اتصال داده:** adapter مصوب و اجرای بازتولیدپذیر بسازد؛ ابتدا در sandbox.
- **بازرس کیفیت:** تازگی، تکرار، شکاف، تغییر schema، واحد، پوشش و نقاط پرت را بررسی و در صورت لزوم سری را quarantine کند.
- **اقتصادسنج:** شاخص مشتق‌شده را با فرمول نسخه‌دار، دادهٔ ورودی مشخص، تست عددی و محدودیت روش بسازد.
- **پژوهشگر بازار/ریسک و ویراستار:** تحلیل و متن فارسی را پیش‌نویس کنند؛ انتشار عمومی تحلیل و رویدادهای رژیمی نیازمند بازبینی مدیر پژوهش است.
- **ناظر عملیات:** سلامت worker/API/پایگاه، شکست‌های تکراری، backup و stale بودن داده را پایش و با شواهد هشدار دهد.

تمام خروجی‌های ماشینی باید ورودی‌ها، منبع، تعریف و واحد، بازه، شمار مشاهدات، زمان تولید، روش هم‌ترازی، فرمول و محدودیت‌ها را ارائه کنند. اگر داده کافی نیست، وضعیت `insufficient_data` ثبت شود. تغییر مقدار تأییدشده یا تعریف شاخص باید تاریخچه و علت داشته باشد. محدودیت‌های دسترسی، شرایط استفادهٔ منبع، CAPTCHA و rate limit دور زده نشوند. مجوز اشتراک در صورت پیاده‌سازی فقط سمت API کنترل شود.

## منابع اجرایی و دستورهای بررسی

- راهنمای اجرای محلی و دامنهٔ داده: `README.md`.
- استقرار استاتیک، انتشار snapshot و مسیر سروری: `docs/DEPLOYMENT.md`.
- نقش‌ها و مرزبندی ایجنت‌ها: `docs/AGENT_WORKFLOWS.md`.
- زمان‌بندی واکشی و retry: `api/app/refresh_data.py`.
- تنظیم مسیر و اتصال SQLite: `api/app/db.py` و `api/app/schema.sql`.
- تولید فایل‌های عمومی: `scripts/export_static_data.py`.
- سرویس‌های API، worker، web و Caddy: `compose.yaml`.
- انتشار GitHub Pages: `.github/workflows/deploy-pages.yml`.

دستورهای متداول از ریشهٔ پروژه:

```sh
# اجرای محیط توسعه با API و worker محلی
npm run dev:all

# اجرای تست‌های API و ingestion
python3 -m pytest -q api/tests

# بررسی کد رابط
npm run lint
npm run typecheck

# خروجی استاتیک از SQLite محلی و build سایت
npm run prepare:static
```

`npm run prepare:static` فایل‌های `public/data/` را بازنویسی می‌کند؛ پیش از هر انتشار باید diff و `snapshot.json` بررسی شود. اجرای این فرمان لاگین، پرداخت یا حفاظت داده ایجاد نمی‌کند. workflow موجود، پس از push مجاز به `main`، فقط build و انتشار GitHub Pages را انجام می‌دهد.

## دروازه‌های کیفیت برای کار ایجنت‌ها

- منبع و مجوز استفاده پیش از افزودن adapter روشن باشد؛ fixture نمونه و تست parser همراه تغییر ثبت شود.
- کیفیت داده حداقل شامل تاریخ آخر، تکرار کلیدها، ترتیب زمانی، واحد، شکاف غیرمنتظره و تغییر schema باشد. کنترل‌ها برای تواتر ماهانه/فصلی با daily متفاوت تنظیم شوند.
- سری تأییدنشده وارد شاخص مشتق‌شده یا snapshot عمومی نشود؛ خطای یک منبع نباید سایر منابع سالم را بی‌صدا خراب کند.
- شاخص جدید باید تعریف اقتصادی، فرمول، نسخه، تست، تاریخچهٔ ورودی و محدودیت تفسیری داشته باشد. همبستگی و سناریو به‌عنوان علیت یا پیش‌بینی قطعی نمایش داده نشوند.
- snapshot پیش از انتشار از نظر `generated_at`، شمار سری/نقاط، اندازه، دادهٔ stale، و تغییرات ناخواسته بررسی شود. تغییرات خروجی عمومی باید در diff قابل بررسی باشند.
- دادهٔ خصوصی، credential، فایل `.env` و پایگاه محلی هرگز وارد Git، `out/` یا `public/data/` نشوند.
- مانیتورینگ باید بین «واکشی موفق»، «مشاهدهٔ تازه از ناشر» و «انتشار تازهٔ سایت» فرق بگذارد و زمان هرکدام را جدا گزارش کند.

## مواردی که هنوز حل نشده‌اند

- زمان‌بند پایدار و میزبانی production برای worker/API انتخاب و فعال نشده است.
- سیاست backup، retention و بازیابی SQLite و مانیتورینگ با هشدار خارج از محیط محلی تعریف نشده است.
- انتشار snapshot فعلاً دستی است و GitHub Actions آن را از پایگاه داده نمی‌سازد.
- چارچوب اجرای ایجنت‌ها، صف وظایف، دسترسی حداقلی ابزارها و ممیزی عملکرد هنوز پیاده‌سازی نشده است.
- احراز هویت، پلن اشتراک، billing و جداسازی محتوای پولی از دادهٔ عمومی وجود ندارد.
- پیش‌بینی‌های مدل‌محور و شاخص‌های ترکیبی سفارشی باید پس از تثبیت provenance، کنترل کیفیت و نسخه‌بندی فرمول وارد محصول شوند.
